# ТЕХНІЧНЕ ЗАВДАННЯ (TECHNICAL SPECIFICATION)
## Проект: Binance Volume Surge Monitor & Telegram Alerter (Ultra-Lightweight)

Цей документ містить повний технічний опис, архітектуру та вимоги для розробки легкого інструменту моніторингу об'ємів торгів криптомонет на біржі Binance в реальному часі з миттєвим сповіщенням у Telegram.

---

### 1. ЗАГАЛЬНИЙ ОПИС ПРОЕКТУ

**Мета проекту:**  
Створення високопродуктивного, ультра-легкого локального додатка, який у реальному часі відстежує ринкові угоди (Trades) на біржі Binance за всіма або вибраними торговими парами (USDT). Головна функція — миттєве виявлення аномального зростання об'єму торгів будь-якої монети на **10%** або більше за короткий проміжок часу (наприклад, 1 хвилину) порівняно з базовим періодом (15 хвилин), та надсилання термінового повідомлення у Telegram-канал/чат, а також відображення цієї інформації у лаконічному веб-інтерфейсі.

---

### 2. ТЕХНОЛОГІЧНИЙ СТЕК (ULTRA-LIGHTWEIGHT TECH STACK)

Для забезпечення максимальної швидкодії, мінімального споживання ресурсів (до 50 МБ RAM на сервері) та відсутності зайвих залежностей обрано такий стек:

*   **Бекенд (Сервер обробки даних):**
    *   **Мова:** Python 3.11+ (з використанням асинхронності `asyncio`).
    *   **Бібліотеки:**
        *   `websockets` (для асинхронної роботи з Binance WebSocket та локального сервера).
        *   `aiohttp` або `httpx` (для асинхронних записів у Telegram Bot API та REST-запитів до Binance).
    *   **Збереження даних:** **In-Memory** (усі розрахунки та ковзні вікна об'ємів торгів зберігаються в оперативній пам'яті у вигляді стандартних структур даних Python — `dict` та `collections.deque`). Жодних баз даних (PostgreSQL, SQLite, Redis) для максимальної швидкості.

*   **Фронтенд (Візуальний дашборд):**
    *   **Структура:** Один файл `index.html` з інтегрованим JavaScript.
    *   **Стилі:** **Pico.css** (або Tailwind CSS) через CDN. Pico.css автоматично застосовує сучасну темну тему (Dark Mode) до стандартних HTML-тегів, що економить час і ресурси.
    *   **Логіка (JS):** Чистий Vanilla JS (ES6+) без збірок (Webpack/Vite) та фреймворків (React/Vue). Використовує нативний `WebSocket` браузера для отримання даних.

---

### 3. АРХІТЕКТУРА ТА ПОТІК ДАНИХ (DATA FLOW)

Система розділена на дві незалежні частини для уникнення перевантаження клієнтського браузера тисячами подій на секунду:

1.  **Бекенд (Слухач Binance):**
    *   При запуску робить REST-запит `GET https://api.binance.com/api/v3/exchangeInfo`, щоб отримати список усіх активних пар до USDT (наприклад, BTCUSDT, ETHUSDT і т.д.).
    *   Відкриває асинхронні комбіновані WebSocket-з'єднання з Binance (Combined Streams) на стрім `@aggTrade` для кожної монети. Формат: `wss://stream.binance.com:9443/stream?streams=btcusdt@aggTrade/ethusdt@aggTrade/...`.
    *   Накопичує об'єми торгів у пам'яті, розраховує зміни об'єму.
    *   При виявленні сплеску на 10%:
        *   Надсилає POST-запит у Telegram Bot API.
        *   Транслює подію у свій локальний WebSocket-сервер (`ws://localhost:8765`).

2.  **Фронтенд (Локальна веб-сторінка):**
    *   Підключається до локального WebSocket-сервера (`ws://localhost:8765`) для миттєвого виведення сповіщень (алертів) у стрічку новин на екрані.
    *   **Для детального перегляду монети:** При кліку на монету зі списку або стрічки а alert-ів, браузер **напряму** підключається до Binance WebSocket для цієї конкретної монети, щоб виводити в реальному часі:
        *   Поточний стакан (Order Book) через стрім `<symbol>@depth` (обмежений до 10-20 рівнів для швидкості).
        *   Останні угоди через стрім `<symbol>@trade`.
    *   Це запобігає перевантаженню фронтенду, оскільки браузер обробляє потоки угод тільки для ОДНІЄЇ монети, яка відкрита на екрані, а не для всіх 400+ одночасно.

### 4. АЛГОРИТМ ВИЯВЛЕННЯ СПЛЕКСУ ОБ'ЄМУ (DETECTION ALGORITHM)

Щоб точно визначати швидкий підскок об'єму на 10% і уникати хибних чи застарілих сигналів:

1.  **Ковзне вікно (Sliding Window):**
    *   Для кожної монети бекенд зберігає історію хвилинних об'ємів за останні 15 хвилин. Це реалізується за допомогою структури `collections.deque(maxlen=15)`.
    *   Кожну хвилину бекенд фіксує накопичений об'єм за цю хвилину та додає його в чергу (deque), видаляючи найстарішу хвилину.

2.  **Розрахунок базового рівня (Baseline Volume):**
    *   Базовий середній хвилинний об'єм ($V_{average}$) обчислюється як середнє арифметичне значення об'ємів за попередні 14 хвилин (індекси 0-13 у черзі).
    *   $V_{average} = \frac{\sum_{i=1}^{14} V_i}{14}$

3.  **Порівняння з поточною хвилиною:**
    *   Поточний об'єм за останню хвилину ($V_{current}$) порівнюється з базовим.
    *   Якщо $V_{current} \ge V_{average} \times 1.10$ (зростання на 10% або більше), реєструється аномалія.
    *   *Примітка для розробника:* Можна додати мінімальний поріг ліквідності у доларах (наприклад, $V_{current} > 10,000\$$), щоб виключити малоліквідні монети ("шиткоїни"), де копійчані угоди можуть викликати сплески на тисячі відсотків.

4.  **Таймаут сповіщень (Cooldown):**
    *   Для запобігання спаму в Telegram після першого сигналу по монеті встановлюється таймаут (Cooldown) тривалістю **5 хвилин**.
    *   Усі подальші тригери для цієї монети ігноруються, поки не мине цей час.

### 5. ФУНКЦІОНАЛЬНІ ВИМОГИ ДО КОМПОНЕНТІВ

#### 5.1. Backend (`server.py`)
*   **Запуск локального сервера:** Створення WebSocket-сервера на порту `8765`.
*   **Ініціалізація:** Отримання списку USDT-пар з Binance ExchangeInfo API. Фільтрація тільки активних (`STATUS: TRADING`) торгових пар.
*   **Отримання даних:** Підключення до Binance Combined WebSockets (`@aggTrade`).
*   **Обробка повідомлень:**
    *   Парсинг JSON: вилучення символу (`s`), ціни (`p`), кількості (`q`), мітки часу (`E`) та параметру `isBuyerMaker` (`m`).
    *   Розрахунок об'єму в USDT: $Volume = Price \times Quantity$.
    *   Оновлення поточної хвилинної суми в пам'яті.
*   **Надсилання сповіщень у Telegram:**
    *   Формат запиту: асинхронний HTTPS POST на `https://api.telegram.org/bot<TOKEN>/sendMessage`.
    *   Шаблон повідомлення:
        ```text
        🚨 SPARK DETECTED! 🚨
        Asset: #{Symbol}
        Price: ${Price}
        Current 1m Vol: ${CurrentVolume}
        Average 15m Vol: ${AverageVolume}
        Increase: +{IncreasePercentage}%
        Market Action: {BuyerPercentage}% Buyers 🟢
        ```
*   **Трансляція на Фронтенд:** Надсилання JSON-повідомлення усім підключеним клієнтам локального WebSocket.

#### 5.2. Frontend (`index.html` + `app.js`)
*   **Інтерфейс (Дашборд):**
    *   **Верхній індикатор:** Статус підключення до локального сервера (Зелений/Червоний).
    *   **Ліва панель ("Стрічка аномалій"):** Вертикальна стрічка карт-сповіщень. Нові сповіщення з'являються зверху з плавною анімацією підсвічування жовтим кольором.
    *   **Центральна панель ("Інтерактивний термінал"):**
        *   Поле пошуку монети.
        *   Кнопка вибору монети.
        *   Візуальний стакан ордерів (Order Book): дві колонки (Bids зеленим, Asks червоним), де динамічно змінюються об'єми на різних рівнях цін. Оновлюється через пряме підключення до Binance API `@depth10@100ms`.
    *   **Права панель ("Останні угоди"):**
        *   Стрічка угод у реальному часі для обраної монети (оновлюється через стрім `@trade`).
        *   Показує ціну, об'єм, час та напрямок (зелений текст — покупка по ринку, червоний — продаж).
*   **Ультра-швидка оптимізація JS:**
    *   Використовувати `document.createElement` та `DocumentFragment` для швидкого оновлення DOM без перемальовування всієї сторінки.
    *   Обмежувати кількість елементів у списках (наприклад, показувати максимум 20 останніх угод та 15 останніх а alert-ів, старі видаляти з DOM), щоб сторінка не споживала пам'ять під час тривалої роботи.

### 7. КРИТЕРІЇ ПРИЙНЯТТЯ ТА ПЕРЕВІРКА ЯКОСТІ

Агент вважається таким, що виконав завдання успішно, якщо:
1.  **Швидкість запуску:** Бекенд запускається миттєво і споживає менше 50 МБ оперативної пам'яті.
2.  **Обробка всіх монет:** Система стабільно тримає з'єднання з Binance Combined WS для 100+ топ-монет (або всіх USDT пар) без втрати пакетів та помилок переповнення буфера.
3.  **Точність а alert-ів:** Сповіщення в Telegram приходять протягом **1-2 секунд** після того, як хвилинний об'єм перевищив ліміт у 10%.
4.  **Стабільність інтерфейсу:** Веб-сторінка плавно оновлює стакан та угоди вибраної монети, процесор клієнта не завантажується більше ніж на 5% при відкритій вкладці.
5.  **Робота без БД:** Вся логіка збереження ковзних вікон реалізована виключно в RAM.
